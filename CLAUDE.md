# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Branch-per-concern layout

This repo (`iamchriswick/devcontainers`) keeps each concern on its own long-lived branch. The branches share no history of each other's files, so merging between them is never the move.

| Branch | Holds |
| --- | --- |
| `main` | Release orchestration workflows only; no feature or template source |
| `features` | Dev Container Features in `src/<id>/` (`devcontainer-feature.json` + `install.sh`), tests in `test/<id>/` and `test/_global/`, CI in its own `.github/workflows/test.yaml` |
| `templates` | Dev Container Templates in `src/<id>/` (`devcontainer-template.json` + `.devcontainer/`), smoke tests in `test/<id>/test.sh` run via `.github/actions/smoke-test` |
| `config` | Dotfiles/helper config (zsh, starship, eza, delta, Claude settings), versioned by release-please (`version.txt`, `CHANGELOG.md`) |

This devcontainer has a single checkout on `main` at `/workspaces/devcontainers`. To work on another concern, read it with `git show <branch>:<path>` / `git ls-tree -r <branch>`, or check it out beside this one with `git worktree add ../<branch> <branch>` and edit there, rather than switching `main`'s checkout.

## Workflows on `main`

Every workflow here is manual (`workflow_dispatch`), named `TEST: ...`, and checks out another branch to do its work:

- `release.yaml`: guarded to `main`; checks out `features`, validates `./src`, packages with `devcontainer features package`, and per feature creates a pinned release `feature_<id>_v<version>` plus a rolling `feature_<id>` release that is deleted and re-pointed each time. An existing versioned release is skipped, so bump `version` in `devcontainer-feature.json` to ship.
- `release_config.yaml`: guarded to `main` + dispatch; runs release-please (`release-type: simple`) against `config`, skipping PR creation. Its `push: branches: [config]` trigger never does anything, because of that guard (and because `config` holds no copy of the file).
- `publish.yaml`: publishes Features to GHCR, but is guarded to `refs/heads/features` while the file lives only on `main`. A dispatch runs the workflow file from the chosen ref, so it fires only once a copy exists on `features`.

Generated-docs PRs from both feature workflows target `features`.

## Testing Features

Neither Docker nor `@devcontainers/cli` is installed in this devcontainer (image `typescript-node`), so these run only where both exist. From a `features` checkout (mirrors `features/.github/workflows/test.yaml`):

```sh
npm install -g @devcontainers/cli
devcontainer features test -f <id> -i debian:latest --skip-scenarios .   # autogenerated test vs one base image
devcontainer features test -f <id> --skip-autogenerated --skip-duplicated .   # scenarios.json only
devcontainer features test --global-scenarios-only .
```

Templates are tested from a `templates` checkout with `.github/actions/smoke-test/build.sh <id>` then `test.sh <id>`.
